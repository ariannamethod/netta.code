# Netta Lee: четвёртый остров, Doom

`nettadoom.py` проводит сгенерированную Python-политику через настоящий ViZDoom.
Lee читает `corpora/doom.txt`, пишет целый скрипт и получает обратную связь после
исполнения его действий. Один скрипт остаётся неизменным на протяжении эпизода.

В текущем окружении движок ViZDoom 1.3.0 завершается при инициализации:
`socket(): Operation not permitted`, затем SIGSEGV. Повторная проверка V3 со
штатным `+use_joystick 0` дала тот же результат. Полная команда и stderr находятся
в `results/doom_v3_joystick_probe/receipt.json`. Здесь игровые эпизоды пока не
состоялись; комплектное `states/doom.json` остаётся начальным состоянием.

## Запуск

Из каталога проекта, в отдельном окружении Python:

```bash
python -m pip install -r requirements-doom.txt
python nettadoom.py doctor --output output/doom_doctor --game-seed 1001
```

`doctor` запускает движок, читает первое состояние и framebuffer, сохраняет PNG
и закрывает игру. Действий политики в этой проверке нет. Коды завершения: `0` —
движок готов, `2` — запуск не состоялся. `train` и `evaluate` выполняют такую же
предварительную проверку до чтения обучаемого состояния и до его записи.

Новую жизнь удобно сначала создать и проверить без игровой зависимости:

```bash
python nettadoom.py check --island corpora/doom.txt \
  --state states/doom-run.json --output output/doom_check \
  --attempts 128 --seed 701
```

Затем обучение:

```bash
python nettadoom.py train --state states/doom-run.json \
  --output output/doom_train_01 --attempts 100 --seed 701 \
  --game-seed 1001 --episode-repeats 3
```

Здесь 100 — число сырых генераций, включая синтаксические ошибки и копии
корпусного поведения. Каждый допустимый новый скрипт играет три эпизода с
заданными последовательными seed. В обучение поступает средняя награда всех
трёх эпизодов, один раз на сгенерированную политику. Повторный запуск с теми же
`--seed`, `--game-seed` и `--episode-repeats`, новым каталогом `--output` и тем же
`--state` продолжает последовательность после `stats.games`.

Зафиксированную жизнь можно оценить отдельно:

```bash
python nettadoom.py evaluate --state states/doom-run.json \
  --output output/doom_evaluate --attempts 64 --seed 90001 \
  --game-seed 80001 --episode-repeats 3
```

`evaluate` сверяет полное состояние до и после каждого скрипта. Случайность
генерации и случайность игрового мира задаются отдельно. Для сравнения состояний
до и после обучения предусмотрен парный запуск:

```bash
python tools/evaluate_doom.py \
  --baseline output/doom_train_01/initial-state.json \
  --trained states/doom-run.json --output output/doom_paired \
  --attempts 64 --generation-seed 90001 --game-seed 80001 \
  --episode-repeats 3
```

Обе жизни получают одинаковые seed генерации и одинаковые игровые старты.
Учитывается каждая попытка. Скрипты, которые не прошли проверку, имеют нулевой
кредит попытки. Отчёт отдельно показывает долю допустимых новых политик,
завершённые эпизоды, убийства и разницу среднего кредита. Интервалы считаются
парным bootstrap; также приводятся числа положительных, отрицательных и равных
разностей и двусторонний sign test. `--check-only` выполняет парное сравнение
кода без ViZDoom; игровые показатели в нём имеют значение `null`.

## Политика и наблюдение

Мир политики — словарь `obs`. Имена и значения сохраняются одинаковыми при
проверке и во время игры:

| Поле | Значения | Источник |
|---|---|---|
| `health` | `25`, `60`, `100` | Здоровье `<=25`, `<=75`, `>75` |
| `ammo` | `0`, `10` | Патроны отсутствуют / присутствуют |
| `scene` | `empty`, `left`, `center`, `right` | Центр крупнейшей видимой метки |

Метки `DoomPlayer`, `Blood`, `BulletPuff` исключены. При одинаковой площади
выбирается меньший идентификатор объекта. Центры ровно на границах третей экрана
относятся к `center`. Получаются ровно 24 возможных входа.

Исходные байты каждого сгенерированного скрипта исполняются на всех 24 входах
в свежих пространствах Python. Выход `action` должен быть одной из шести строк:
`turn_left`, `turn_right`, `move_forward`, `strafe_left`, `strafe_right`, `shoot`.
Скрипт должен выдавать хотя бы два разных действия. Таблица, совпадающая с
поведением любого скрипта корпуса, помечается `corpus_behavior_replay`.
Переименование переменных и добавление мёртвого кода эту проверку не обходят.

Во время эпизода используется полная таблица фактически исполненного скрипта.
Её ключи, значения и хеш проверяются до передачи движку. Таблица покрывает весь
допустимый входной мир; каждой строке действия соответствует одна кнопка на
четыре игровых тика. Сведения о среде задаёт `doom.json`.

Награда одного эпизода вычисляется по изменениям переменных движка:

```text
score = kills - 0.01 * damage - 0.005 * ammo_spent
reward = 0.5 + 0.5 * tanh(score / 3)
```

В журналах также сохраняется необработанная награда ViZDoom. Ошибка движка
получает `reward: null`; `observe` не вызывается. Если один из повторных эпизодов
оборвался, вся группа остаётся без обучающего обновления, а уже полученные
траектории сохраняются. Синтаксическая ошибка самой политики получает обычный
нулевой кредит.

V3 передаёт в `observe` хеш всей таблицы поведения и диагностику ошибки
исполнения. При успешном исполнении и средней награде выше `0.5` жизнь может
приобрести локальные продолжения программы. Одинаковая таблица добавляет их
один раз; повторные игровые последствия продолжают менять оценку решений.

## Проверки V3 и сохраняемые данные

`results/doom_v3_paired_identity/` содержит проверку парного оценщика на двух
загрузках одного начального состояния: 32 одинаковые пары, по 14 новых
реактивных политик с каждой стороны, 10 совпадений с корпусом, 7 синтаксических
ошибок и 1 ошибка исполнения. Все парные разности равны нулю; обе жизни
сохранились без изменений. Запуск выполнен с `--check-only`.

Все 20 тестов завершились успешно (`results/tests_doom_v3.log`). Тесты проверяют
точные действия на 24 входах, границы восприятия, повреждение
таблицы, сохранение отступов, копирование поведения, среднюю награду всех
повторов, отмену обновления при частичном сбое, неизменность жизни при
предварительном отказе движка, приобретение продолжений через настоящий
`Organism.observe` на явно заданном тестовом результате и отсутствие игровых
оценок у проверки кода.

Для каждой политики сохраняются `candidate.py` и `receipt.json`; для каждого
игрового эпизода — `trajectory.jsonl`, `episode.json`, кадры и stdout/stderr
движка. `engine-request.json` фиксирует фактическую таблицу и конфигурацию,
`engine-process.json` — команду процесса, его исход и хеш моста. Нативный
процесс отделён от процесса обучения; при превышении времени его группа
процессов завершается в POSIX-среде.
